# PEP 448 — Generalised Unpacking

**Branch:** `pep448`
**Date:** 2026-03-02
**Issue:** #216 (`{**a, 'key': val}` throws `NotImplementedError` at parse time)
**Status:** ✅ Complete

---

## Problem

PEP 448 (Python 3.5) extended unpacking generalizations to collection literals and
function/method calls. Monty blocked all of them at parse time with `not_implemented!`.

The blocked cases were:

| Feature                                                        | Location blocked   |
|----------------------------------------------------------------|--------------------|
| `{**a, 'k': v}` dict literal with unpack                       | `parse.rs:721`     |
| `[*a, 1, *b]` list literal with unpack                         | `parse.rs:962`     |
| `(*a, 1)` tuple literal with unpack                            | `parse.rs:962`     |
| `{*a, 1}` set literal with unpack                              | `parse.rs:962`     |
| `f(*a, *b)` / `f(0, *a, 3)` multiple or non-final `*` in calls | `parse.rs:832,839` |
| `f(**a, **b)` multiple `**` in calls                           | `parse.rs:1032`    |

## Design

### New opcodes (2 total)

| Opcode       | Operand    | Stack effect | Semantics                                                                             |
|--------------|------------|--------------|---------------------------------------------------------------------------------------|
| `DictUpdate` | `u8 depth` | −1           | Pop mapping, **silently merge** into dict at `depth` (later wins). For dict literals. |
| `SetExtend`  | `u8 depth` | −1           | Pop iterable, add all items to set at `depth`. Follows `ListExtend` pattern.          |

No new opcodes for function call kwargs — the existing `DictMerge` (which already raises
TypeError on duplicate keys) is chained for multiple `**kwargs`.

### Semantic distinction: dict literals vs function call kwargs

| Context              | Opcode                 | Duplicate key        |
|----------------------|------------------------|----------------------|
| `{**a, **b}` literal | `DictUpdate` (new)     | Later wins, no error |
| `f(**a, **b)` call   | `DictMerge` (existing) | TypeError raised     |

This matches CPython's behaviour per PEP 448.

### IR changes — shared enums

Two new IR enums added to `expressions.rs`:

```rust
/// Item in a list/tuple/set literal — either a plain value or a starred unpack.
pub(crate) enum SequenceItem { Value(ExprLoc), Unpack(ExprLoc) }

/// Item in a dict literal — either a key/value pair or a double-star unpack.
pub(crate) enum DictItem { Pair(ExprLoc, ExprLoc), Unpack(ExprLoc) }
```

`Expr::List`, `Expr::Tuple`, `Expr::Set` now hold `Vec<SequenceItem>`.
`Expr::Dict` now holds `Vec<DictItem>`.

Two new call-arg enums added to `args.rs`:

```rust
/// A single positional argument in a generalised call.
pub enum CallArg   { Value(ExprLoc), Unpack(ExprLoc) }

/// A single keyword argument in a generalised call.
pub enum CallKwarg { Named(Kwarg), Unpack(ExprLoc) }
```

`ArgExprs` gains a new variant:

```rust
GeneralizedCall { args: Vec<CallArg>, kwargs: Vec<CallKwarg> }
```

The parser switches to `GeneralizedCall` when it encounters a second `*`, positional args
after `*`, or a second `**`.

### Compiler strategy

**Collection literals** — two-path compilation:

- **No unpack** (common case): unchanged — `BuildList(N)` / `BuildTuple(N)` / `BuildSet(N)` / `BuildDict(N)`.
- **Has unpack** — emit `Build*(0)` then per-item:

| Item type                              | Opcodes                          |
|----------------------------------------|----------------------------------|
| `DictItem::Pair(k, v)`                 | push k, push v, `DictSetItem(0)` |
| `DictItem::Unpack(e)`                  | compile e, `DictUpdate(0)`       |
| `SequenceItem::Value(e)` (list/tuple)  | compile e, `ListAppend(0)`       |
| `SequenceItem::Unpack(e)` (list/tuple) | compile e, `ListExtend`          |
| `SequenceItem::Value(e)` (set)         | compile e, `SetAdd(0)`           |
| `SequenceItem::Unpack(e)` (set)        | compile e, `SetExtend(0)`        |
| Tuple end                              | `ListToTuple`                    |

**Generalised function calls (`GeneralizedCall`):**

```
Build args tuple:
  BuildList(0)
  for each CallArg:
    Value(e)  → compile_expr + ListAppend(0)
    Unpack(e) → compile_expr + ListExtend
  ListToTuple

Build kwargs dict (if any kwargs present):
  BuildDict(0)
  for each CallKwarg:
    Named(k,v)  → push_str_key + compile_expr + BuildDict(1) + DictMerge(func_name_id)
    Unpack(e)   → compile_expr + DictMerge(func_name_id)

CallFunctionExtended / CallAttrExtended(flags)
```

`DictMerge` raises TypeError on duplicate keys — this covers all cases correctly, including
`f(x=1, **{'x': 2})` and `f(**{'x': 1}, x=2)`.

## Implementation Notes / Deviations from Plan

### `type_error_value_after_star` vs `type_error_not_iterable`

CPython 3.14 uses a **different error message** for the two contexts:

| Context                    | Message                                                 |
|----------------------------|---------------------------------------------------------|
| `[*42]` / `(*42,)` literal | `TypeError: Value after * must be an iterable, not int` |
| `{*42}` set literal        | `TypeError: 'int' object is not iterable`               |
| `f(*42)` call              | uses existing `type_error_not_iterable`                 |

A new helper `ExcType::type_error_value_after_star` was added to `exception_private.rs` for
the list/tuple literal context. `list_extend` uses this helper (it's called from the
`ListExtend` opcode emitted for literal unpack). Set literals still use
`type_error_not_iterable` in `set_extend`.

### Error test format: `# Raise=` not `TRACEBACK:`

The 5 new error test files use `# Raise=` rather than the preferred `TRACEBACK:` format.
This is intentional — not a quality shortcut. The reasons:

1. **Dict/set unpack caret mismatch**: CPython 3.14 emits no caret for `{**42}` / `{*42}`;
   Monty emits one. A single `TRACEBACK:` block cannot satisfy both interpreters.
2. **Function duplicate kwargs prefix**: The `TRACEBACK:` runner uses `runpy.run_path(run_name='__main__')`,
   which causes CPython to prefix user-defined function names with `__main__` in error messages
   (e.g. `__main__.f() got multiple values…`). Monty does not inject this prefix.
   `# Raise=` uses `py.run()` which does not apply the prefix.

The `# Raise=` format still verifies the exception type and message against both CPython and
Monty, giving real coverage.

## Known Limitations (follow-up work)

- **Non-dict mappings**: PEP 448 allows `{**x}` for any object with `keys()` +
  `__getitem__`. Monty only supports `HeapData::Dict` as an unpack source. Unblocked
  once user-defined classes land — `dict_update` will need to call the mapping protocol.

- **`[*x for x in items]` is a `SyntaxError` in Python** (explicitly excluded during PEP
  448 design) — not a Monty limitation.
